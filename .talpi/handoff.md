사람이 검수를 이어서 하려고 그대로 두기로 정했다(2026-08-23). 되돌리는 방법:


않는다. **이 상태를 커밋하지 말 것.** 세 항목짜리 등록부로 테스트와 빌드가

  **두 모습 모두에서** 실제로 배선되어 있는 것(17·24 — `keyNav.test.ts` 는

  방향키가 초점을 옮기지 않는 것(29).

- 전체 화면 목록에서 **엔터를 누가 처리하는가**. 목록 항목은 진짜 링크라
  브라우저가 활성화하지만, 씬의 방울에는 그런 기본 동작이 없어 전역 처리가
  필요하다. 두 경로가 같은 코드를 쓰면 링크에서 이중 발동 위험이 생기고,
  나누면 "키의 뜻은 하나"라는 계약의 글자와 어긋나 보인다. 스텝 1 의 핀은
  "전역 처리가 스스로 이동했다면 기본 동작을 반드시 막았어야 한다"로 두
  갈래를 모두 허용해 두었다.

## 페이즈 4 보고에 실을 것

- **스크린 리더를 쓰는 방문자에게는 씬에서 작품으로 들어가는 길이 없다.**
  방향키가 그 사람의 읽기 키라 씬 커서를 움직일 수 없고(Ledger 가 인정한
  대가), 씬을 드러내는 숨은 목록의 항목은 링크가 아니라 활성화할 수도 없다.
  결국 그에게 작품으로 가는 유일한 길은 "아이콘 → 슬라이드 → 항목"이다.
  Ledger 는 "그 사람들을 위해 씬이 탭 정거장 하나로 존재하고 B6 가 조작법을
  읽어준다"까지만 적어 두었고, 작품에 닿는 길이 목록 하나뿐이어도 되는지는
  적지 않았다. 숨은 항목을 `tabIndex={-1}` 링크로 만들면 길이 하나 더
  생기지만 Requirement 11("씬은 탭 정거장 하나")의 경계에 바싹 붙는다.
- 작품이 하나뿐인 지금, 홈에서 방향키를 눌러도 커서가 그 방울에서 움직이지
  않는다. 스펙대로(순환) 동작하는 것이지만, 처음 온 방문자가 "방향키로 방울
  사이를 옮기고"라는 안내를 읽거나 듣고 눌렀을 때 아무 변화가 없으면 안내가
  거짓말처럼 느껴질 수 있다. VoiceOver 로는 같은 문장이 반복해 들린다.
  등록부가 둘 이상이 되면 저절로 사라지는 문제다.
- **contract candidate**: "마우스만 쓴 방문자에게 키보드 안내는 끝까지 화면에
  없다". Requirement 43 의 절반이 부정 명제라, 나중에 누가 안내를 항상 보이게
  바꿔도 조용히 통과한다.
- **contract candidate**: "모션 축소 상태에서 등장 연출의 지속시간이 0 이다".
  스텝 4 가 `hint-enter` 에서 실제 드리프트를 발견해 고친 자리다. 인라인
  `animation` 축약값이 지속시간을 변수로 받는지 검사하는 드리프트 가드가
  `siteTitle.test.ts` 와 같은 성격으로 값을 할 만하다.
- **contract candidate**: "화면에 실시간 알림 영역은 언제나 하나". 지금은 씬
  갈래와 폴백 갈래가 배타적이라는 구조적 사실로만 참이고, 어느 갈래에 영역이
  하나 더 늘면 조용히 깨진다.
- 폴백 안내 띠는 `<main>`(전체 화면 목록이 이고 있다) **바깥**의 형제로
  그려진다. 랜드마크로 건너뛰며 읽는 방문자는 알림을 놓친 뒤 그 문구를 다시
  찾기 어렵다. 안으로 넣으려면 `WorksList` 에 안내를 주입하는 prop 이
  필요한데 "소유하는 쪽은 보여주는 쪽을 모른다"의 반대 방향이라 두지 않았다.
  계약이 요구하는 것은 "알려진다"까지라 위반은 아니다. VoiceOver 확인에서
  걸리면 다시 볼 자리다.
- **조작법 문구의 Esc 가 씬에서는 실제로 아무 일도 하지 않는다.**
  `KEYBOARD_HINT` 는 "…Esc를 누르면 돌아옵니다"인데, 씬 정거장에서 Esc 는
  무동작이다(Esc 는 열린 목록을 닫고 작품 페이지에서 나온다). 스펙 43 이
  "방향키·엔터·Esc"를 함께 알리라고 해서 사이트 전체 규칙으로 적었는데,
  씬에서만 듣는 사람에게는 살짝 어긋나는 약속이다.

- **B6 ⑥ 의 두 문구를 다른 강도로 핀했다.** 씬 폴백 안내는 "알려진다"(live
  region 또는 초점 이동)로, 빈 등록부 문구는 "낭독 표면에 존재한다"로
  잡았다. 근거는 방문자가 겪는 일이 다르다는 것이다 — 폴백 안내는 요청하지
  않은 화면 변화의 설명이라 스스로 찾아 읽을 이유가 없고, 빈 등록부 문구는
  스스로 연 목록 안에 있어 목록에 닿으면 읽힌다. 스펙 29 의 "그 사실이
  **소리로도** 전달된다"를 폴백 안내와 같은 강도로 읽어야 한다면 빈 문구
  쪽도 알림 요구로 올려야 하고, 그러면 지금 통과하는 핀 두 개가 실패로
  바뀐다.

## Gotchas

- **목록이 열리면 아이콘이 렌더되지 않으므로 `aria-expanded` 로 열림 상태를
  알리는 표준 수단을 쓸 수 없다.** 남는 것은 초점을 목록 안으로 옮기거나
  실시간 알림을 두는 것이다. 초점을 옮기는 선택은 Requirement 20(Esc 로
  닫으면 초점이 아이콘으로 돌아감, `sceneShell.test.tsx` 가 이미 핀함)과
  맞물리므로 함께 봐야 한다.

- **`src/keys/useSceneKeyNav.ts` 의 `focusedByKeyboard(element)` 는 브라우저의
  `:focus-visible` 판정이다.** 스텝 4 가 목록에서도 재사용할 만하다.
- **`keyNav` 는 이벤트 타깃을 모른다.** 목록 안에 버튼 같은 요소가 생기면
  스페이스 `preventDefault` 가 그 요소의 표준 동작을 가로챌 수 있으므로,
  타깃 판별은 리스너를 다는 쪽이 해야 한다. 지금 `WorksList` 카드는 `<a>` 라
  당장 걸리는 자리는 없다.

- **씬 없는 환경에서 `HOME_TESTID` 는 이제 어디에도 뜨지 않는다.** 페이즈 2
  스텝 2 가 `/` 를 `/works` 로 갈아치우면서 `HomeFallback` 이 사라졌기
  때문이다. 라우팅 단언은 `topRoutePath`
  (`router.state.matches[0].route.path`)로 옮겨 두었다. 앞으로 "홈으로
  간다"를 확인할 때 `HOME_TESTID` 를 쓰면 항상 null 이라 공허하게 통과한다.
- **`/works` 라우트 요소는 `<WorksList variant="fullscreen" />` 하나로 둔다.**
  `fullscreen` 이 이미 `<main>` 을 그리므로 바깥에서 또 감싸면 `main` 이
  둘이 된다.

- **jsdom 은 언제나 WebGL 이 없다.** `isWebGLAvailable()` 이 항상 false 라
  테스트는 늘 "씬을 못 띄우는" 경로를 탄다. 페이즈 2 이후에는 그 경로가
  `/works` 전체 화면 목록이 되므로, 기존 라우팅 테스트의 "홈으로 간다" 단언이
  `/` 와 `/works` 를 구별할 수 있어야 한다. 목록 화면에 자기 표식이 필요한
  이유다.
- **`getContext` 를 참으로 속이지 말 것.** R3F 캔버스가 진짜로 마운트되면서
  three.js 가 죽는다. 이전 런이 `src/scene/webgl.ts` 프로브를 Canvas 마운트
  *전* 게이트로 둔 것도 같은 이유다.
- **`src/test-setup.ts` 를 지우지 말 것.** jsdom 의 AbortController 를 Node
  네이티브로 교체하는데, 없으면 react-router 리다이렉트 테스트가 깨진다.
- **`bun run build` 가 가장 싼 기계적 확인이다** (`tsc -b && vite build`).
- **`tsconfig.node.json` 의 include 에 `src/theme.ts` 가 들어 있다.** vite
  설정이 `transformIndexHtml` 로 사이트 제목을 치환하느라 theme 을 임포트해서
  생긴 프로젝트 경계다. 건드리면 `tsc -b` 가 TS6307 로 실패한다.
- **이전 런의 규약 문서 원본**은 `.talpi/archive/2026-08-22/conventions-prev-run.md`
  에 있다. 거기 있던 모듈 지도는 `.talpi/codemap.md` 로 옮겼다.
